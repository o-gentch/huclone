# Аудит приложения Huclone

Дата: 2026-11-07. Состояние: ветка `main`, коммит `f4dc62b`.
Метод: статическое чтение всего кода (~4.8k строк, из них ~1.5k собственного кода). Приложение не запускалось, тесты не гонялись (гемы локально не установлены). Пункты, требующие проверки в рантайме, отмечены ⚠️.

## 1. Что это за приложение

**Huclone — «AI-клон автора»**: пользователь загружает свои тексты (посты, Telegram-экспорт), система строит «карту личности» и стиль автора, после чего чат отвечает от первого лица, в голосе автора, опираясь на его материалы (RAG).

Стек: Rails 8.1, PostgreSQL + pgvector (`neighbor`), Solid Queue / Solid Cable / Solid Cache, Hotwire (Turbo + Stimulus), importmap, Tailwind, Slim, ruby-openai, Kamal + Docker.

## 2. Функциональность

| Область | Что есть | Где |
|---|---|---|
| Персоны | Создание персоны (имя + опциональный system_prompt). Корень `/` редиректит на первую персону | `PersonasController` |
| Загрузка контента | Ручной ввод текста или файл; авто-заголовок (60 симв.); массовое добавление («добавить ещё») | `ContentsController` |
| Импорт Telegram | Парсинг `result.json` канала; фильтры: длина ≥100, отсев таймкодов и постов-ссылок | `Imports::Telegram`, `Imports::Filters` |
| Обработка контента | Чанкинг (1500 симв., overlap 200) → эмбеддинги `text-embedding-3-small` → pgvector | `Contents::Processor`, `Chunker` |
| Лингвистика | Статистика без LLM: топ-слова, длины предложений, словарное богатство, эмодзи, пунктуация | `Personas::LinguisticsAnalyzer` |
| Карта личности | Map-reduce через LLM: батчи по 25 → промежуточные группы по 10 → финальный JSON (gpt-4o). Инкрементальное слияние при новых текстах (`included_in_map`) | `PersonalityMapBuilder` |
| Эталонные посты | До 7 самых «длинных» (по числу чанков) материалов помечаются exemplars; 3 из них идут в промпт при `write_post` | `ExemplarSelector`, `ContextBuilder` |
| Чат | Стриминг ответа через Turbo Streams / Action Cable; optimistic UI на Stimulus | `ChatResponder`, `chat_controller.js` |
| Intent-классификация | gpt-4o-mini определяет тип запроса (пост / идеи / структура / small talk / вопрос) → разный промпт и глубина истории | `IntentClassifier` |
| Режимы ответа | `strict` (по материалам) / `ideas` (свободнее) | `Message::MODES` |
| RAG | Top-5 чанков по косинусной близости, подмешиваются в user-сообщение | `Ai::RagSearch` |
| Операции | Mission Control Jobs на `/jobs`, health `/up`, PWA-манифест, Kamal-деплой, CI (brakeman, bundler-audit, rubocop) | |

Чего **нет**: аутентификации и пользователей, удаления/редактирования персон и диалогов, редактирования контента, списка диалогов с управлением, пересборки карты вручную, отображения статуса обработки/карты в UI (частично, ⚠️ не проверялось), тестов, документации.

## 3. Оценка архитектуры

### Что сделано хорошо

- **Чёткое разделение слоёв.** Тонкие контроллеры, логика в сервисах (`Ai::`, `Contents::`, `Conversations::`, `Personas::`, `Imports::`), долгие операции в джобах. Для проекта такого размера это читаемо.
- **Правильный выбор «скучного» стека.** Solid Queue/Cable/Cache + Postgres означают один стор вместо Redis; pgvector вместо отдельной векторной БД. Минимум инфраструктуры — хорошо для соло-проекта.
- **Продуманный пайплайн персонализации.** Многоступенчатая карта личности (map-reduce) + инкрементальное слияние + детерминированная лингвистика без LLM + exemplars + intent-зависимые промпты — это осмысленный дизайн, а не «один большой промпт».
- **Устойчивость джобов.** `retry_on` с polynomial backoff для rate-limit, `limits_concurrency` на сборку карты (1 на персону), отдельные очереди с разными пулами потоков, статусная машина контента с CHECK-констрейнтом в БД, идемпотентность `Processor` (`return if done?`).
- **Стриминг через Turbo Streams** без самописного JS-протокола; HTML экранируется (`CGI.escapeHTML`) на сервере и клиенте.
- **Эксплуатация:** Kamal, Dockerfile, health-check, фильтрация параметров, CI со security-сканерами, логирование токенов/латентности эмбеддингов.

### Что вызывает вопросы

1. **Нет модели пользователя и авторизации.** В `personas` есть `user_id` без FK и без использования. Любой, кто достучался до приложения, видит и меняет всё; `Persona.find(params[:persona_id])` не скоупится ни на что. Для «персонального» инструмента на localhost терпимо, для деплоя через Kamal — нет (см. §4).
2. **Персона = один автор, но структура допускает мульти-тенантность наполовину.** Корень отдаёт `Persona.first`, а остальной код притворяется мульти-персонным. Нужно определиться: single-user инструмент или SaaS.
3. **Карта личности хранится одним JSONB-блобом и целиком вкладывается в каждый system prompt** (`map.to_json`), включая ≥10 дословных цитат. Это растёт с каждым merge (LLM просят «не терять старое», а «при противоречиях сохранять оба»), т.е. размер карты монотонно увеличивается без верхней границы.
4. **Пайплайн карты — «всё или ничего» внутри одного джоба.** Лингвистика + N батчей + промежуточные + финал в одной транзакции жизни джоба; падение на последнем шаге теряет все результаты предыдущих вызовов LLM (промежуточные наблюдения нигде не кешируются).
5. **Состояние «карта строится» не смоделировано.** Есть только `personality_map_built_at`; нет статуса/ошибки/прогресса, поэтому UI не может честно показать «строится / устарела / упала».
6. **Тесты отсутствуют полностью** (`test/` пуст, кроме `test_helper.rb`) при том, что в коде много недетерминированной логики и работы с внешним API. Сервисы уже принимают зависимости (`embeddings:`, `ai_client:`) — архитектура к тестам готова, их просто нет.
7. **Смешение ответственностей в `ChatResponder`**: классификация, RAG, сборка промптов, стриминг, рендер HTML и обработка ошибок в одном классе; HTML-рендер живёт в сервисе, а не во вью/хелпере.
8. **Роутинг:** `config/routes.rb` содержит висящую строку `get ` без аргументов перед `resources :personas`. ⚠️ Ruby может разобрать это как `get(resources(...) do ... end)`, т.е. вложенные ресурсы окажутся в блоке `get`. Нужно запустить `bin/rails routes` и убедиться, что маршруты корректны; в любом случае строку надо удалить.

## 4. Узкие места и риски

Приоритет: 🔴 критично, 🟠 важно, 🟡 желательно.

### Безопасность

- 🔴 **Нет аутентификации вообще** + деплой через Kamal. Любой посетитель читает чужие тексты, удаляет контент, запускает платные вызовы OpenAI (денежный DoS).
- 🔴 **`/jobs` (Mission Control) ⚠️.** В `development.rb` basic auth отключён, `base_controller_class` переопределён на `ApplicationController`. В production нужно проверить, что настроены креды для basic auth; иначе панель либо недоступна, либо (при ослаблении) открыта всем. Через неё можно перезапускать/удалять джобы.
- 🟠 **Нет лимитов на ввод:** размер файла в `ContentsController#create` и `TelegramImportsController` читается целиком в память (`file.read`); нет ограничения на длину сообщения в чате, на число постов в импорте. Один большой Telegram-экспорт = тысячи джобов и эмбеддингов.
- 🟠 **Prompt injection из пользовательских данных.** Тексты автора и RAG-фрагменты подставляются в промпты без разметки границ; `Persona#system_prompt` из формы есть в схеме и контроллере, но (судя по коду `ContextBuilder`) не используется — мёртвое поле.
- 🟡 `config/initializers/openai.rb` падает при загрузке, если `credentials.openai` отсутствует (`nil[:access_token]`) — ломает `assets:precompile`/CI без ключей.
- 🟡 `deploy.yml` содержит заглушки (`192.168.0.1`, `localhost:5555`) — перед реальным деплоем нужна настройка; `SOLID_QUEUE_IN_PUMA: true` означает, что веб и воркеры делят один процесс (см. ниже).

### Производительность и масштабирование

- 🟠 **Последовательные эмбеддинги + `sleep(0.1)`** в `Contents::Processor`: один HTTP-вызов на чанк. Для длинного текста — десятки секунд. OpenAI принимает массив `input` — батчинг даст кратное ускорение и снизит число запросов.
- 🟠 **Транзакционность `Processor`:** чанки создаются по одному; при падении посреди обработки статус возвращается в `pending`, но уже созданные чанки остаются, а при ретрае создаются заново → **дубликаты чанков** (нет `destroy_all` перед пересозданием и нет уникального индекса `(content_id, position)`). Это напрямую портит RAG-выдачу.
- 🟠 **Нет векторного индекса.** В `chunks.embedding` нет HNSW/IVFFlat; поиск — точный seq scan с JOIN на `contents`. На десятках тысяч чанков (Telegram-канал) задержка чата вырастет линейно.
- 🟠 **Латентность чата** складывается из трёх последовательных вызовов: intent (gpt-4o-mini) → эмбеддинг запроса → gpt-4o. Первый токен виден только после первых двух. Intent и эмбеддинг независимы — можно запускать параллельно.
- 🟠 **Стриминг через Solid Cable с `polling_interval: 0.1s` и полной перерисовкой** (`broadcast_update_to` отправляет весь накопленный текст на каждый токен): трафик и нагрузка на БД растут квадратично от длины ответа; на каждый токен — запись в таблицу cable. Стоит троттлить (раз в 50–100 мс) или слать дельты (`append`).
- 🟠 **Блокировка воркеров на долгих стримах:** очередь `chat` — 5 потоков; 5 одновременных ответов занимают весь пул. Кроме того, при `SOLID_QUEUE_IN_PUMA` джобы конкурируют с веб-запросами за CPU/память одного хоста; 10+5+5 потоков воркеров плюс Puma на одном маленьком сервере — тесно.
- 🟡 `Conversation#recent_messages` и `messages.chronological.last(n)` — `last(n)` на отсортированном relation делает ORDER DESC LIMIT, ок, но `recent_messages` загружает все сообщения при `order(...).last(limit)` в некоторых путях; метод не используется — удалить.
- 🟡 `ExemplarSelector` грузит все `done`-контенты с `includes(:chunks)` только чтобы посчитать длину. Достаточно `COUNT` по чанкам или `length(body)` в SQL. Также критерий «больше чанков = лучший образец стиля» — слабый прокси: он выбирает самые длинные посты, а не самые характерные.
- 🟡 `LinguisticsAnalyzer` читает **весь корпус в память и пересчитывает с нуля** при каждой сборке карты; токенизация `[а-яёa-z]+` не учитывает морфологию (русские словоформы считаются разными словами), стоп-лист мал, а `top_words` не используется нигде, кроме JSON в `personas.linguistics` — ⚠️ не видно, чтобы лингвистика попадала в промпт (в `ContextBuilder` её нет). Если это так — затраты на вычисление и поле GIN-индекс на `linguistics` бесполезны.

### Качество LLM-пайплайна

- 🟠 **Лингвистика не используется в генерации** (см. выше) — лучшая «жёсткая» часть стилевой модели не влияет на ответы.
- 🟠 **Размер контекста не контролируется.** system prompt = инструкции + вся карта + 3 полных exemplar + история + 5 чанков по 1500 симв. Нет подсчёта токенов и отсечения; на длинных постах возможен выход за лимит или лишние расходы. Exemplars подставляются целиком без ограничения длины.
- 🟠 **Нет защиты от «обрыва» map-reduce:** `extract_observations_in_parallel` молча отбрасывает упавшие батчи (`filter_map` + лог). Карта строится по неполным данным, а `contents.update_all(included_in_map: true)` помечает **все** материалы как учтённые, включая те, чьи батчи упали → они не попадут в карту никогда (при `delta_build` — тем более).
- 🟠 **Инкрементальные слияния деградируют:** каждый merge — пересказ JSON моделью; через десятки итераций возможен дрейф, потеря цитат и раздувание. Нет периодической полной пересборки и нет валидации схемы JSON результата (`JSON.parse` без проверки ключей; при невалидном ответе `JSON::ParserError` не покрыт `retry_on`).
- 🟠 **Каждая загрузка текста запускает `BuildPersonalityMapJob`** (в `ContentsController#create`) **и** ещё раз по завершению обработки. Первый запуск стартует, пока контент ещё `pending` и в карту не попадает — пустая работа и лишние LLM-вызовы (на пустой корпус `return`, но на непустом — реальная трата). Достаточно одного триггера из `signal_completion`.
- 🟡 **Хардкод моделей** (`gpt-4o`, `gpt-4o-mini`, `text-embedding-3-small`) разбросан по сервисам; смена модели = правки в 4 файлах. Размерность 1536 прошита в схеме.
- 🟡 Intent-классификатор по каждому сообщению — лишний платный вызов; для первой версии можно заменить эвристикой/функцией и вызывать LLM только при неоднозначности.
- 🟡 Промпты жёстко на русском и вшиты в код; нет версионирования, нет оценки качества (evals), поэтому любое изменение промпта «вслепую».

### Надёжность и корректность

- 🟠 **Потеря сообщения при ошибке чата:** `ChatResponder` при исключении пишет «Произошла ошибка» и **делает `raise`**, значит срабатывает `retry_on` (3 попытки) — пользователь видит ошибку, затем ответ может внезапно «перезаписаться» успешным; при ретрае повторно тратятся intent+embedding. Нужно выбрать одну семантику.
- 🟠 **Нет идемпотентности стрима:** при ретрае `accumulated` начинается заново, а `assistant_message` остаётся тем же — окей, но если джоб упал после частичного стрима, клиент мигает. Также в `ChatResponder` ошибки `OpenAI::Error` ловятся общим `rescue => e`.
- 🟠 **Нет «кнопки стоп»/таймаута** для ответа и нет индикации, что ответ завис (assistant-сообщение с пустым `body` остаётся навсегда, если джоб убит/потерян).
- 🟡 Два последовательных `create!` сообщений в `MessagesController` не в транзакции; при падении между ними — осиротевшее user-сообщение.
- 🟡 `Content#destroy` на персоне с тысячами чанков — `dependent: :destroy` грузит и удаляет по одному (N+1); использовать `delete_all` через FK `ON DELETE CASCADE`.
- 🟡 Импорт Telegram глушит **все** `StandardError` (`rescue StandardError → skipped += 1`) — ошибки БД/кода маскируются под «пропущено». Плюс нет дедупликации: повторный импорт того же файла создаёт дубли контента и платит за эмбеддинги заново.
- 🟡 `Chunker` режет по символам, а не по токенам/предложениям/абзацам; для постов с эмодзи и кириллицей границы чанков могут резать смысл. Бóльшая часть постов (<1500 симв.) = 1 чанк, т.е. чанкинг реально работает только на длинных текстах.
- 🟡 Фронтенд: в `chat_controller.js` закомментированный код блокировки формы; `hello_controller.js` — шаблонный остаток; `#thinking-indicator` удаляется ли после первого дельта-обновления — ⚠️ проверить в UI (в JS видно только создание).

### Процесс / качество кода

- 🔴 **0 тестов.** Нет ни одного теста при наличии CI-джоба (⚠️ проверить, запускает ли он `bin/rails test` — в `ci.yml` вероятно да, и тогда он «зелёный» вхолостую).
- 🟠 README — шаблонный. Нет инструкции по запуску, переменным окружения, структуре пайплайна.
- 🟡 Мёртвый код/поля: `personas.user_id`, `personas.system_prompt` (не используется в промпте), `Conversation#recent_messages`, `hello_controller`, `jbuilder`, `image_processing`, неиспользуемые маршруты `conversations#new`, `personas#index` с пустым состоянием.
- 🟡 Смешанные языки: код и комментарии на английском, UI-строки в контроллерах на русском, `en.yml` пустой — i18n не используется, строки захардкожены.
- 🟡 Сырые SQL/ORM-запросы повторяются (`Content.where(persona_id:, status: "done")` в 3 местах) — вынести в scope `Persona#contents.done`.

## 5. Рекомендуемый порядок работ

**Сначала (блокеры деплоя):**
1. Исправить `routes.rb` (удалить `get `), проверить `bin/rails routes`.
2. Закрыть доступ: аутентификация (хотя бы HTTP Basic / Rails 8 `bin/rails generate authentication`) для всего приложения и `/jobs`; скоупить персоны на пользователя.
3. Лимиты: размер файла, длина сообщения, число постов в импорте, rate-limit на `messages#create`.

**Затем (корректность данных):**
4. `Processor`: удалять существующие чанки перед пересозданием, добавить уникальный индекс `(content_id, position)`, батчить эмбеддинги.
5. `PersonalityMapBuilder`: помечать `included_in_map` только реально учтённые материалы; валидировать JSON карты; убрать лишний триггер в `ContentsController`.
6. HNSW-индекс на `chunks.embedding` (`USING hnsw (embedding vector_cosine_ops)`).

**Потом (качество и скорость):**
7. Подключить `linguistics` в `ContextBuilder` (или удалить расчёт).
8. Параллелить intent + embedding; троттлить стриминг-бродкасты.
9. Ограничить размер карты и exemplars по токенам; периодическая полная пересборка карты.
10. Тесты: сервисы (с подменой клиента), джобы, один системный тест чата; полноценный README.

**Можно отложить:** вынос моделей/промптов в конфиг, i18n, оценка качества ответов (evals), UI-статус сборки карты.
