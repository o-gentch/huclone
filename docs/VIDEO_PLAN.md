# Видео как источник знаний — техплан

Статус: черновик на согласование. Код не написан.

## 1. Как я понимаю задачу

**Продукт.** Пользователь (например, инфобизнесмен) загружает записи своих выступлений, конференций, вебинаров. Система:

1. превращает видео в текст с разметкой «кто говорит» и таймкодами;
2. определяет, какой из говорящих — **сам пользователь** (персона), и отделяет его речь от речи остальных;
3. дополняет **карту личности** (стиль, убеждения, метафоры) на основе его устной речи — так же, как сейчас это делается по постам;
4. расширяет **пул знаний**: всё, что он рассказал, попадает в поиск и доступно в чате;
5. позволяет потом работать с этими знаниями как с материалом для книги/курса: просить структуру, оглавление, главы, выжимки по темам, «что я говорил про X на разных конференциях».

**Ключевое отличие от постов** — три вещи:
- **Несколько спикеров.** Нужно понять, кто из них «наш», и не подмешать в его стиль чужую речь.
- **Устная речь ≠ письменная.** Слова-паразиты, повторы, оборванные фразы, расшифровка с ошибками. Для знаний это шум, для стиля — отчасти сигнал (как он говорит), но не то же самое, что как он пишет.
- **Объём.** Конференция — часы речи, десятки тысяч слов на видео; сотни тысяч слов на корпус. Текущий пайплайн (батчи по 25 постов, плоский поиск по чанкам) на это не рассчитан.

**Что остаётся неизменным:** персона, чат, карта личности, RAG, джобы, аутентификация.

## 2. Что нужно уточнить (влияет на выбор)

1. **Речь других спикеров** (модератор, вопросы из зала, соведущий) — хранить как знания «с пометкой чьё», или выбрасывать? Моя рекомендация: хранить в базе знаний с пометкой спикера, но в карту личности **не** подавать.
2. **Языки** — только русский или смешанные? (влияет на выбор ASR).
3. **Объёмы** — типичная длина видео и сколько видео на пользователя (1 ч × 20 vs 6 ч × 200 — разные цены и архитектура хранения).
4. **Облако или своя инфраструктура** — можно ли отправлять аудио внешним сервисам (приватность, договоры)? Есть ли GPU?
5. **Источник** — только загрузка файлов, или ещё ссылки (YouTube, Zoom-записи, Google Drive)?
6. **Стиль из речи и из постов** — одна общая карта или две (письменный голос / устный голос)? Рекомендую одну карту с отдельной секцией `spoken_style`.
7. **Кто определяет «наш спикер»** — готовы ли вы просить пользователя один раз подтвердить себя (послушать 10-секундный фрагмент и нажать «это я»)?

## 3. Целевой пайплайн

```
Загрузка → Извлечение аудио → Транскрипция + диаризация → Сопоставление спикеров с персоной
        → Нормализация речи → Сегменты (Content/Chunk) → Эмбеддинги → Карта личности + База знаний
        → Структурирование знаний (темы, резюме) → Чат / книга
```

Стадии — отдельные джобы с явным статусом (`uploaded → extracting → transcribing → awaiting_speaker_confirmation → processing → done / failed`), чтобы можно было повторить любую стадию и показать прогресс в UI.

### 3.1. Загрузка и хранение
- Active Storage + объектное хранилище (S3-совместимое), **прямая загрузка из браузера** (direct upload) — видео на гигабайты нельзя гнать через Rails.
- Возобновляемая/чанковая загрузка (Uppy + tus/S3 multipart) — на нестабильных соединениях иначе будут обрывы.
- Исходное видео нужно только для извлечения аудио: после обработки можно хранить лишь аудио (или удалять всё по желанию пользователя — вопрос приватности).

### 3.2. Извлечение аудио
- `ffmpeg`: моно, 16 кГц, сжатый формат (opus/mp3). Часовое видео → десятки МБ вместо гигабайт.
- Нарезка на куски по паузам (≤10–15 мин, с небольшим перекрытием) для сервисов с лимитом размера и для параллельной обработки.
- Нужен `ffmpeg` в Docker-образе; тяжёлая работа — в отдельной очереди с небольшим числом потоков.

### 3.3. Транскрипция и диаризация

| Вариант | Как | Плюсы | Минусы |
|---|---|---|---|
| **A. Облачный API «всё в одном»** (AssemblyAI, Deepgram, ElevenLabs Scribe и т.п.) | Один вызов → текст + спикеры + таймкоды + слова | Быстрее всего в разработке; качество диаризации высокое; нет своей ML-инфраструктуры | Платно за минуту; данные уходят третьей стороне; зависимость от вендора |
| **B. OpenAI-транскрипция + отдельная диаризация** | ASR от OpenAI (уже есть ключ и клиент), диаризация другим сервисом, склейка по таймкодам | Один основной вендор для текста | Склейка по таймкодам даёт ошибки на границах; два сервиса вместо одного |
| **C. Свой сервис (Python: WhisperX + pyannote)** | Микросервис на GPU, Rails вызывает по HTTP | Дёшево на больших объёмах; данные остаются у вас; полный контроль | Нужны GPU и ML-эксплуатация; сложнее деплой; качество на русском надо проверять |

**Рекомендация:** начать с **A** за интерфейсом-адаптером (`Transcription::Provider`), чтобы потом заменить на C при росте объёмов. Выбор вендора — по бенчмарку на 2–3 ваших реальных записях (качество русского и диаризации; это нужно измерить, а не угадывать).

Результат хранится в **нормализованном виде**, независимо от вендора:
`Recording` → `Utterance(speaker_label, start_ms, end_ms, text, confidence)`.

### 3.4. Определение «нужного» спикера (главный продуктовый вопрос)

Диаризация даёт метки `SPEAKER_0/1/2` **внутри одного видео**; между видео метки не связаны. Варианты:

| Вариант | Как работает | Плюсы | Минусы |
|---|---|---|---|
| **1. Ручное подтверждение** | После транскрипции UI показывает по каждому спикеру 2–3 коротких фрагмента (аудио + текст) и долю речи; пользователь выбирает «это я» (можно «никто из них») | Просто, надёжно, не нужна биометрия; работает сразу | Один клик на каждое видео; не масштабируется на сотни видео |
| **2. Эталон голоса (voiceprint)** | Пользователь один раз даёт образец своего голоса (или подтверждает первое видео); для остальных видео система сравнивает эмбеддинги голоса спикеров с эталоном | Полностью автоматически после настройки; масштабируется | Нужна модель эмбеддингов голоса (pyannote/ECAPA или API с такой функцией); ошибки при плохом звуке; **биометрические данные** — вопросы согласия и хранения |
| **3. Эвристика** | «Самый говорящий спикер» или «тот, кто представился» | Нулевая стоимость | Часто неверно (модератор, панельные дискуссии) — годится только как **подсказка по умолчанию** |
| **4. Гибрид (рекомендую)** | Эвристика предлагает кандидата → пользователь подтверждает в первом видео → из подтверждённых фрагментов строится voiceprint → на следующих видео авто-сопоставление, а при низкой уверенности — вопрос пользователю | Минимум ручной работы, при этом надёжно | Самый объёмный по реализации |

**План по этапам:** MVP = вариант **1** (+ эвристика как подсказка); вариант **2/4** — вторая фаза, когда будет видно, сколько видео реально грузят. Это снимает самый рискованный пункт, не блокируя запуск.

Состояние `awaiting_speaker_confirmation` — отдельная стадия: пайплайн останавливается и ждёт пользователя, остальная обработка (эмбеддинги чужих реплик) может идти параллельно.

### 3.5. Нормализация устной речи
- Склейка соседних реплик одного спикера в «выступление» (абзацы по паузам и смене темы).
- Очистка: слова-паразиты, заикания, повторы — **в копии для знаний**; исходный сырой текст сохраняется для анализа стиля.
- Пунктуация и абзацы (если вендор не даёт — LLM-проход по кускам).
- Подстановка терминов/имён из словаря пользователя (частая проблема ASR).

### 3.6. Куда попадают данные (два канала)

1. **Карта личности** — только речь выбранного спикера, сегменты по ~500–1500 слов. Подаётся в тот же `PersonalityMapBuilder`, но:
   - в наблюдения добавляется поле «устный контекст» (как объясняет, любимые разговорные обороты, юмор, реакции на зал);
   - в карту — секция `spoken_style`; письменные и устные примеры не смешиваются в `verbatim_examples` (разметить `source: post|speech`).
2. **База знаний** — речь всех спикеров с пометкой `speaker` и таймкодом; чанки с эмбеддингами, как сейчас. Поиск в чате по умолчанию — по речи персоны + релевантным вопросам из зала для контекста.

### 3.7. Структурирование знаний (то, ради чего всё затевается)
Плоского top-5 чанков **недостаточно** для запросов «составь структуру книги по всем конференциям». Нужен иерархический слой:

- **Резюме по сегментам → по видео → по всему корпусу** (иерархическая суммаризация, как в RAPTOR): дерево «корпус → темы → подтемы → цитаты с таймкодами».
- **Тематическая карта**: LLM или кластеризация эмбеддингов выделяет темы; хранится как `Topic` с ссылками на чанки.
- **Новый режим чата/инструмент «книга»:** по запросу собирает оглавление из дерева тем, затем главу за главой раскрывает, подтягивая релевантные чанки и **цитируя источник** (видео + таймкод).
- **Ссылки на источник** в ответах: «из выступления X, 34:12» — доверие и возможность проверить.

### 3.8. Изменения в схеме (эскиз)

```
recordings        persona_id, title, status, duration_s, language, source_type, error
  (+ Active Storage: исходное видео и аудио)
speakers          recording_id, label, is_persona (bool), speech_share, voiceprint (vector, nullable)
utterances        recording_id, speaker_id, start_ms, end_ms, text, confidence
contents          + recording_id (nullable), + speaker_id, + source_kind: post|speech, + start_ms/end_ms
topics            persona_id, parent_id, title, summary, position
topic_chunks      topic_id, chunk_id
```
Идея: речь выбранного спикера материализуется как `Content` (kind=speech) — тогда **весь существующий пайплайн** (чанки, эмбеддинги, карта) переиспользуется почти без изменений.

### 3.9. Что придётся изменить в существующем коде
- `Content`: тип источника, ссылка на запись/таймкоды; `PersonalityMapBuilder` — учёт `source_kind`.
- `Chunker`: для речи резать по репликам/паузам, а не по символам; сохранять таймкод чанка.
- `RagSearch`: фильтр по спикеру/источнику; возврат метаданных для цитирования.
- `ContextBuilder`: секция `spoken_style`; режим «книга».
- Очереди: отдельные `media` (ffmpeg) и `transcription` с малым числом потоков, чтобы тяжёлые задачи не блокировали чат.
- Деплой: ffmpeg в образе, объектное хранилище, лимиты тела запроса/Thruster, отдельный воркер-хост при росте.

## 4. Варианты общей архитектуры

**Вариант I. Монолит + внешний ASR (рекомендую для старта).** Всё остаётся в Rails; транскрипция и диаризация — через облачный API за адаптером; ffmpeg в образе. Плюсы: минимум нового, быстрый запуск, переиспользование всего. Минусы: стоимость растёт линейно с минутами; зависимость от вендора.

**Вариант II. Монолит + Python-сервис для медиа.** Rails хранит и оркестрирует, отдельный сервис (FastAPI + WhisperX + pyannote) делает ASR, диаризацию и voiceprint. Плюсы: данные у вас, дешевле на объёме, voiceprint «из коробки». Минусы: GPU, второй язык и деплой, ML-поддержка.

**Вариант III. Полностью асинхронный конвейер с оркестратором (Temporal/и т.п.).** Для сотен часов в день. Для текущего масштаба — избыточно.

**Рекомендация:** I → при росте объёмов или требованиях по приватности перейти на II, не меняя остальной код (граница — интерфейс `Transcription::Provider` и `Speakers::Matcher`).

## 5. Этапы реализации

**Этап 0 — исследование (2–3 дня).** Прогнать 2–3 ваших реальных записи через 2–3 вендора; сравнить качество русского, диаризацию и цену за час. Решить пункты из §2.

**Этап 1 — видео → текст (MVP-основа).**
- Модели `Recording`/`Speaker`/`Utterance`, direct upload, ffmpeg, адаптер транскрипции, статусы и UI прогресса.
- Готово, когда: загруженное видео превращается в размеченную по спикерам расшифровку, которую можно просмотреть.

**Этап 2 — выбор спикера и подключение к текущему пайплайну.**
- UI подтверждения «это я» (фрагменты, доля речи), материализация речи как `Content(kind: speech)`, нормализация, чанки с таймкодами, эмбеддинги.
- Расширение карты: `spoken_style`, разметка источника цитат.
- Готово, когда: после загрузки видео и подтверждения чат отвечает на вопросы по его содержанию со ссылкой на таймкод, а карта обновляется.

**Этап 3 — структурирование знаний.**
- Иерархические резюме, `Topic`-дерево, режим «книга» в чате, экспорт структуры (Markdown).
- Готово, когда: по запросу «составь оглавление книги по всем конференциям» выдаётся дерево тем со ссылками на источники.

**Этап 4 — масштаб и автоматизация.**
- Voiceprint и авто-сопоставление спикеров, импорт по ссылке, словарь терминов, ретраи/резюмирование по стадиям, мониторинг стоимости.

## 6. Риски

| Риск | Что делать |
|---|---|
| Ошибки диаризации (смешение спикеров, особенно при перебивании) | Подтверждение пользователем; показ уверенности; возможность поправить границы/переназначить реплики |
| Качество русского ASR на жаргоне/терминах | Бенчмарк на этапе 0; словарь терминов; постредактура LLM |
| Стоимость (ASR + эмбеддинги + LLM на сотнях тысяч слов) | Оценка до запуска, лимиты на пользователя, батчи, кэш промежуточных результатов |
| Приватность (чужие голоса, биометрия, содержание выступлений) | Согласие, возможность удалить медиа после обработки, шифрование в хранилище, явное решение по voiceprint |
| Смешивание голосов разных людей в карте | Только подтверждённый спикер идёт в карту; при низкой уверенности — карантин до ручной проверки |
| Деградация поиска на большом корпусе | HNSW уже добавлен; иерархические резюме; фильтры по записи/спикеру |
| Блокировка очередей тяжёлыми задачами | Отдельные очереди и лимиты конкурентности |
| Загрузки на гигабайты | Direct upload + multipart, лимиты и проверка типов |

## 8. Принятые решения (по итогам обсуждения)

- **Язык:** только русский. **Длина видео:** ~20 минут (часовые — редкий случай), поэтому нарезка аудио на куски на MVP не нужна: 20–60 мин аудио в opus/mp3 моно — 5–15 МБ, укладывается в лимиты ASR-сервисов.
- **Облако:** отправка аудио внешним сервисам разрешена. GPU нет → **Вариант I** (монолит + облачный ASR с диаризацией за адаптером).
- **Источник:** только загрузка файлов (ссылки — позже).
- **Выбор спикера:** ручное подтверждение пользователем (эвристика «самый говорящий» — как подсказка по умолчанию). Voiceprint — не в MVP.
- **Вопросы от других спикеров:** хранятся и **учитываются**. Единица знаний — не одиночная реплика, а **«ход диалога»**: вопрос другого спикера + ответ персоны, нарезаются и индексируются вместе (в чанке сохраняется пометка, кто задал вопрос и кто ответил). В карту личности попадает только речь персоны, но вопрос передаётся LLM как контекст («на этот вопрос автор ответил так»), чтобы не терять смысл ответа.
- **Одна карта или две:** одна карта личности с отдельной секцией `spoken_style`; цитаты помечены `source: post|speech`. Выбор стиля — по намерению запроса: для `write_post` берётся письменный голос и посты-образцы, для диалога/ответов на вопросы — устный.
