## 0. Контекст проекта

**Huclone** — Rails 8.1 приложение «AI-клон автора»: пользователь загружает тексты (посты), система строит «карту личности» и отвечает в чате в голосе автора с опорой на его материалы (RAG). Стек: PostgreSQL + pgvector (`neighbor`), Solid Queue/Cable/Cache, Hotwire (Turbo Streams + Stimulus), Slim, Tailwind, importmap, `ruby-openai`, Kamal. Аутентификация — Rails authentication; персоны принадлежат пользователю (`Current.user.personas`). UI-тексты — на русском. Видение и сравнение вариантов — `docs/VIDEO_PLAN.md`. `AUDIT.md` — аудит до правок: большинство 🔴/🟠 пунктов из него уже исправлено (роуты, аутентификация, лимиты, дедупликация чанков, HNSW, валидация карты, параллельный intent+RAG, троттлинг стрима, лингвистика в промпте); открытыми остаются вопросы масштаба карты и контекста — они учтены в §5 ниже.

**Основные существующие части, с которыми придётся работать:**

| Что | Где |
|---|---|
| Модели | `Persona` (`personality_map` jsonb, `linguistics` jsonb), `Content` (`body`, `title`, `sources` jsonb, `status` pending/processing/done/failed, `is_exemplar`, `included_in_map`), `Chunk` (`text`, `position`, `embedding` vector(1536), HNSW-индекс, уникальный `(content_id, position)`), `Conversation`, `Message` |
| Обработка контента | `Contents::Processor` (чанки → батч-эмбеддинги → атомарное пересоздание), `Contents::Chunker` (по символам, 1500/200), `Ai::Embeddings.fetch_many`, `ProcessContentJob` (по завершении всех материалов запускает `BuildPersonalityMapJob`) |
| Карта личности | `Personas::PersonalityMapBuilder` (map-reduce: батчи по 25 материалов → промежуточные → финал; инкрементальный merge через `included_in_map`; валидация ключей карты), `Personas::LinguisticsAnalyzer`, `Personas::ExemplarSelector` |
| Чат | `Conversations::ChatResponder` (intent + RAG параллельно, стриминг в Turbo Streams), `IntentClassifier`, `ContextBuilder` (системный промпт: карта, лингвистика, эталоны, режим, intent), `Ai::RagSearch` (top-5 по косинусу) |
| Очереди | `config/queue.yml`: `content_processing`(10 потоков), `personality_map`(5), `chat`(5) |
| Тесты/CI | Minitest, `bin/rails test`, `bin/rubocop`, `bin/brakeman`. Fixtures: `users(:one)`, `users(:two)`; хелпер `sign_in_as` |

**Как запускать тесты локально:** нужен Postgres с pgvector. На машине владельца по умолчанию работает Postgres 14 без pgvector; рабочий вариант — Postgres 17 на порту 5433:

```bash
export LC_ALL=en_US.UTF-8 PGPORT=5433 PGHOST=localhost
bin/rails db:prepare && bin/rails test && bin/rubocop
```
(по окончании остановить: `pg_ctl ... stop`).

**Ветка:** всё предыдущее (правки аудита, аутентификация, планы) уже слито в `main`. Работать от актуального `main`; каждую задачу — отдельной веткой (`feature/recordings-transcription`, `feature/video-knowledge`) с отдельным PR.

## 1. Принятые решения (не пересматривать)

- **Только облачные API**, своих моделей и GPU нет. Аудио отправлять внешним сервисам разрешено.
- **Язык:** только русский. **Длина видео:** обычно ~20 минут, редко до часа. Нарезка аудио на куски в MVP **не нужна** (аудио mono/16 кГц/opus ≈ 5–15 МБ).
- **Источник:** только загрузка файлов пользователем.
- **Выбор спикера:** вручную пользователем (по коротким фрагментам). Эвристика «больше всех говорит» — только предвыбор в UI. Voiceprint/автосопоставление между видео — **вне объёма**.
- **Вопросы других спикеров учитываются:** единица знаний — «ход диалога» (вопрос другого спикера + ответ персоны). В карту личности попадает **только речь персоны**; вопрос передаётся LLM как контекст.
- **Одна карта личности** с новой секцией `spoken_style`; цитаты помечаются `source: post|speech`. Для `write_post` используется письменный голос и посты-образцы; для диалога/ответов — устный.
- **ASR-провайдер:** за адаптером `Transcription::Provider`. Реализовать **один** реальный провайдер — по умолчанию **AssemblyAI** (REST: загрузка файла, транскрипт с `speaker_labels`, `language_code: "ru"`, опрос статуса или webhook; в ответе `utterances` с `speaker`, `start`/`end` в мс, `text`). Перед реализацией **сверить актуальную документацию** (модель/язык, параметры, цены) и при расхождении выбрать Deepgram (Nova, `diarize=true`, `language=ru`) — интерфейс адаптера от этого не меняется. Ключ — `ENV["ASSEMBLYAI_API_KEY"]` (или credentials), по аналогии с `config/initializers/openai.rb`. В тестах — фейковый провайдер по записанным JSON-фикстурам; **реальные платные вызовы в тестах запрещены**.
- Ориентир стоимости: ~$0.20 за 20-минутное видео, ~$0.50 за час (на ASR приходится больше половины).

# ЗАДАЧА 1. Видео → размеченная по спикерам расшифровка + выбор «своего» спикера

**Цель:** пользователь загружает видео/аудио, система извлекает звук, получает расшифровку с разметкой «кто говорит» и таймкодами, показывает прогресс, и пользователь вручную подтверждает, какой спикер — он сам. Результат задачи — подтверждённая запись (`Recording`) с нормализованными репликами. **Подключение к карте личности и поиску — не в этой задаче** (Задача 2).

## 1.1. Модель данных (миграции + `db/schema.rb`)

```
recordings   persona_id (FK, not null), title, status (string + CHECK),
             duration_ms, language (default "ru"), error_message,
             provider, provider_job_id, raw_transcript (jsonb, ответ провайдера),
             timestamps
speakers     recording_id (FK), label (string, "A"/"B"... как у провайдера),
             is_persona (bool, default false), speech_ms (int), words_count (int),
             unique(recording_id, label)
utterances   recording_id (FK), speaker_id (FK), position (int), start_ms, end_ms,
             text (text), confidence (float, nullable),
             index(recording_id, position)
```
- Статусы `Recording`: `uploaded → extracting_audio → transcribing → awaiting_speaker_confirmation → confirmed` и `failed` (с `error_message`). Допустимые значения — через enum и CHECK-констрейнт, как у `Content.status`.
- Файлы — **Active Storage**: `has_one_attached :source_file` (оригинал) и `has_one_attached :audio_file` (извлечённое аудио). В схеме **ещё нет таблиц Active Storage** — выполнить `bin/rails active_storage:install`, миграцию закоммитить. В production `config.active_storage.service = :local` с volume `/rails/storage`; сделать сервис настраиваемым и описать в README переход на S3-совместимое хранилище (конфиг, не реализация).
- Оригинал **удаляется** после успешного извлечения аудио (настройка `Recording::KEEP_SOURCE = false`); аудио хранится.
- `Persona has_many :recordings, dependent: :destroy`; дочерние записи удаляются каскадом (`delete_all`/FK ON DELETE CASCADE, не по одной).

## 1.2. Загрузка
- Контроллер `RecordingsController` (вложен в `personas`, поиск персоны только через `Current.user.personas`): `index`, `new`, `create`, `show`, `destroy`. `create` принимает файл через **Active Storage direct upload** (браузер → хранилище), форма на Stimulus с прогресс-баром.
- Валидации: типы `video/mp4`, `video/quicktime`, `video/webm`, `video/x-matroska`, `audio/mpeg`, `audio/mp4`, `audio/wav`, `audio/ogg`; максимум **2 ГБ**; проверять и content-type, и сигнатуру/ffprobe. Лимит длительности — 3 часа (проверка по `ffprobe`), иначе `failed` с понятным сообщением.
- Минимум UI: список записей персоны со статусами и авто-обновлением (Turbo Stream broadcast при смене статуса), страница записи, кнопка «Повторить» для `failed`, удаление. Пункт «Видео» в навигации (`app/views/layouts/application.html.slim`). Тексты — на русском, стиль как в существующих вьюхах.

## 1.3. Пайплайн (джобы, каждая стадия идемпотентна)
1. `ExtractAudioJob` (очередь **`media`**, добавить в `config/queue.yml`, 2 потока, 1 процесс): `ffmpeg` → mono, 16 кГц, opus (или mp3) ~32–48 kbps; сохранить в `audio_file`, записать `duration_ms` (ffprobe), удалить оригинал; статус → `transcribing`. Вызывать ffmpeg через `Open3` с массивом аргументов (без shell-интерполяции), с таймаутом; stderr — в лог/ошибку.
2. `TranscribeRecordingJob` (очередь **`transcription`**, 3 потока): через `Transcription::Provider` отправить аудио, дождаться результата (опрос с backoff **или** webhook — предпочтителен опрос, т.к. нет публичного URL в dev; не блокировать поток воркера sleep-циклом дольше разумного — перепланировать джоб с `retry_job wait:`), сохранить `raw_transcript`, создать `Speaker` и `Utterance` (в транзакции, повторный запуск пересоздаёт, не дублирует), посчитать `speech_ms`/`words_count` по спикерам. Статус → `awaiting_speaker_confirmation`.
3. Ошибки: сетевые/429/5xx провайдера — `retry_on` с `polynomially_longer`; после исчерпания — `failed` + `error_message` (`after_discard` по образцу `ProcessContentJob`). Необратимые (битый файл, нет речи) — сразу `failed`.

## 1.4. Адаптер транскрипции
```
Transcription::Provider            # интерфейс: #submit(audio_io_or_url) -> job_id; #fetch(job_id) -> Result | :pending
Transcription::Result              # Struct: utterances [{speaker:, start_ms:, end_ms:, text:, confidence:}], duration_ms, raw
Transcription::AssemblyAi          # реальная реализация (Faraday, уже есть в зависимостях через ruby-openai)
Transcription::Fake                # для тестов: читает JSON из test/fixtures/files/transcripts/*.json
Transcription.provider             # выбирается конфигом (ENV/credentials), по умолчанию AssemblyAI; в test — Fake
```
Нормализация (`Transcription::Normalizer`): склеить подряд идущие реплики одного спикера с паузой < ~2 с; отбросить пустые; привести спикеров к меткам `A`, `B`, ….

## 1.5. Подтверждение спикера (UI + логика)
- Страница записи в статусе `awaiting_speaker_confirmation`: по каждому спикеру — доля речи (%), число слов, 2–3 **коротких репрезентативных фрагмента** (самые длинные реплики, обрезанные до ~200 символов) с таймкодом и кнопкой «▶ прослушать» (HTML5 `<audio>` по `audio_file` с `#t=start,end` или `currentTime`); предвыбран спикер с наибольшей долей речи.
- Действия: «Это я» для одного спикера (или «Меня нет в этой записи»), затем «Подтвердить». Поддержать переименование спикера (необязательное поле `display_name`, например «Ведущий»).
- Подтверждение: в транзакции проставить `is_persona`, статус → `confirmed`, затем поставить в очередь `ProcessRecordingJob` — **пока это заглушка/хук**, реализуемый в Задаче 2 (в Задаче 1 достаточно `Recordings::Confirm` с TODO-вызовом через `Recordings::Pipeline.after_confirm(recording)`, который по умолчанию ничего не делает).
- Просмотр расшифровки (read-only): реплики по порядку с таймкодами и цветом/именем спикера.

## 1.6. Инфраструктура и качество
- `Dockerfile`: установить `ffmpeg` (и `ffprobe`) в runtime-образ; README — для локальной разработки (`brew install ffmpeg`).
- Проверить лимиты размера запросов (Thruster/Puma/прокси) — direct upload их обходит, но убедиться в корректности CSP/CORS для direct upload (`config/initializers/content_security_policy.rb`).
- Brakeman: нет небезопасного вызова команд и открытого доступа к файлам; доступ к `audio_file` — только владельцу персоны (скачивание через контроллер или подписанные URL с коротким TTL, не публичные).
- Тесты (Minitest, **без обращений к реальным сервисам**): модели и статусы; `Normalizer`; `TranscribeRecordingJob` с `Transcription::Fake` (создание спикеров/реплик, идемпотентность, ошибки → `failed`); `ExtractAudioJob` на маленьком тестовом аудио-фикстуре (пропускать тест, если `ffmpeg` не найден — `skip`); контроллер: авторизация (чужая персона → 404, аноним → редирект), валидации типов/размера, подтверждение спикера. `bin/rubocop` и `bin/brakeman` чистые.

## 1.7. Критерии приёмки Задачи 1
- Загрузка 20-минутного видео из браузера; запись проходит статусы до `awaiting_speaker_confirmation` без ручного вмешательства; прогресс виден в UI.
- Пользователь видит спикеров с фрагментами и аудио, выбирает «Это я», подтверждает; в БД `is_persona` выставлен у одного спикера, статус `confirmed`.
- Повтор джобов не создаёт дублей; сбой провайдера даёт понятный `failed` и работающую кнопку «Повторить».
- Чужой пользователь не видит и не слышит записи.
- Тесты, rubocop, brakeman зелёные; реальные платные вызовы не используются в тестах; в README описаны `ASSEMBLYAI_API_KEY`, ffmpeg и хранилище.
- Выполнены обязательные меры из §5 с пометкой «Задача 1» (квоты, watchdog зависших записей, закрытая отдача файлов, дедупликация загрузок, ограничение конкурентности ffmpeg).

**Вне объёма:** voiceprint/автосопоставление, импорт по ссылке, правка границ реплик, нарезка длинных файлов, редактирование текста расшифровки.

# ЗАДАЧА 2. Знания и карта личности из подтверждённых записей + структурирование для «книги»

**Зависит от Задачи 1.** **Цель:** превратить подтверждённую запись в (а) пул знаний с поиском и цитатами с таймкодами, (б) вклад в карту личности (`spoken_style`), (в) иерархическую структуру тем для запросов вида «составь оглавление книги по всем выступлениям».

## 2.1. Ходы диалога → Content/Chunk
- `Recordings::TurnBuilder`: из `utterances` собирает **ходы**: последовательности «реплики других спикеров (вопрос) → реплики персоны (ответ)». Ответ персоны, длиннее порога, режется по паузам/смене темы на фрагменты ~300–1500 слов; вопрос прикрепляется к первому фрагменту ответа. Если персона говорит без вопроса (доклад) — просто сегменты её речи. Реплики других спикеров без ответа персоны сохраняются как знания только если их доля значимая (параметр; по умолчанию — не создавать отдельные Content).
- Миграция `contents`: `kind` (`post`|`speech`, default `post`, CHECK), `recording_id` (FK, nullable), `start_ms`, `end_ms`, `context_text` (text, nullable — вопрос другого спикера), `speaker_name` (nullable). Существующий код считает все Content постами — **пройтись по всем местам** (`Content.exemplars`, `LinguisticsAnalyzer`, `ExemplarSelector`, `ContextBuilder`, `ContentsController#index`, `ProcessContentJob.signal_completion`) и явно решить для каждого: учитывать `speech` или нет. Решения по умолчанию: `ExemplarSelector` — только `post`; `LinguisticsAnalyzer` — только `post` (письменные метрики), для речи считать отдельный блок `spoken` (средняя длина реплики, доля вопросов и т.д.) или не считать в этой задаче.
- `body` для `speech` = очищенный текст ответа (без слов-паразитов/повторов — LLM-проход `gpt-4o-mini` пачками, с жёстким промптом «не менять смысл, не добавлять»; сырой текст остаётся в `utterances`). В `sources` — `{type: "recording", recording_id:, start_ms:, end_ms:}`. Лимит 1 МБ из `ContentsController` не применяется (контент создаётся сервисом).
- Чанкинг речи: `Contents::Chunker` расширить режимом для `speech` (по границам предложений/реплик, размер ~1000–1500 символов); у каждого `Chunk` хранить таймкод начала (`chunks.start_ms`, миграция) и в эмбеддинг/текст чанка включать вопрос (`context_text`) — чтобы поиск находил ответ по формулировке вопроса. Остальное — существующий `Contents::Processor`.
- `ProcessRecordingJob` (подставляется в хук `Recordings::Pipeline.after_confirm` из Задачи 1): TurnBuilder → создать `Content(kind: speech, status: pending)` → `ProcessContentJob` на каждый → по завершению сработает существующий `BuildPersonalityMapJob`. Идемпотентность: повторное подтверждение/запуск удаляет прежние `Content` этой записи (с чанками) и создаёт заново.

## 2.2. Карта личности: устный стиль
- `PersonalityMapBuilder`: батчинг **по размеру текста (токены/символы), а не по числу материалов** (речевые сегменты крупнее постов). В промпт извлечения для `speech` передавать `context_text` (вопрос) как контекст и просить выделять: любимые разговорные обороты, как объясняет, юмор, реакции на аудиторию, структуру ответа. Добавить в схему карты секцию `spoken_style` (`filler_habits`, `explanation_patterns`, `typical_phrases`, `humor`, `audience_interaction`) и поле источника у `verbatim_examples` (`{text, source: "post"|"speech"}` — обновить валидацию `REQUIRED_MAP_KEYS`/промпты и обратную совместимость со старыми картами без секции).
- `ContextBuilder`: секция `spoken_style` в системный промпт; **выбор голоса по intent**: `write_post` — письменный голос и посты-образцы (`kind: post`), `casual_chat`/`answer_question`/`structure_knowledge`/`generate_ideas` — с учётом устного стиля. Примеры цитат подмешивать с учётом источника.

## 2.3. Поиск и цитаты
- `Ai::RagSearch`: возвращать чанки вместе с метаданными (`content.kind`, `recording_id`, `start_ms`, название записи); поддержать фильтры (по записи, по виду источника). Для речи — подмешивать вопрос из `context_text`.
- `ChatResponder`: в RAG-контексте помечать фрагменты источником («Из выступления «…», 34:12»), промпт требует ссылаться на источник там, где опирается на фрагмент. В UI сообщения ассистента — список источников (название записи, таймкод, ссылка на страницу записи с якорем на момент).
- Увеличить `TOP_K` для запросов типа `structure_knowledge` (параметр по intent) при условии лимита токенов; ограничить суммарный размер RAG-контекста (символы), чтобы не раздувать промпт.

## 2.4. Структурирование знаний («книга»)
- Миграции: `topics` (`persona_id`, `parent_id`, `title`, `summary`, `position`, `depth`), `topic_chunks` (`topic_id`, `chunk_id`), `recordings.summary` (text).
- `Knowledge::SummarizeRecordingJob`: резюме по записи (map-reduce по её `speech`-Content, `gpt-4o-mini`). `Knowledge::BuildTopicTreeJob` (очередь `personality_map` или новая `knowledge`, `limits_concurrency` 1 на персону): по резюме и эмбеддингам чанков строит дерево тем (до 3 уровней): сначала кластеризация эмбеддингов (простая: k-means/агломеративная на стороне Ruby либо LLM-группировка резюме), затем названия/резюме тем одним LLM-вызовом на кластер; привязка чанков к темам; перестройка при добавлении записей (пересборка всего дерева — приемлемо на текущих объёмах, указать в комментарии).
- Новый intent и режим чата **`book`** (расширить `IntentClassifier::INTENTS`, `HISTORY_LIMITS`, `ContextBuilder::INTENT_INSTRUCTIONS`, режимы/переключатель в `conversations/_form.html.slim`): для запросов «оглавление/глава/структура книги» отвечать на основании дерева тем + релевантных чанков, с цитатами. Минимум: (а) оглавление из дерева; (б) раскрытие главы по теме с подтягиванием её чанков (до лимита токенов).
- Страница «Темы» (`TopicsController#index`, read-only): дерево тем с резюме, число источников, ссылки на фрагменты; кнопка «Экспорт в Markdown» (оглавление + резюме тем + список источников с таймкодами).

## 2.5. Стоимость и ограничения
- Логировать токены/стоимость по этапам (как `Ai::Embeddings`); ограничить параллелизм LLM-вызовов (`MAX_CONCURRENT`), `retry_on` для 429.
- Защита от дублей: `recording_id`+диапазон времени уникальны для `Content(kind: speech)`.

## 2.6. Тесты и критерии приёмки Задачи 2
- Юнит-тесты: `TurnBuilder` (доклад без вопросов; вопрос→ответ; несколько вопросов подряд; ответ длиннее порога режется), расширенный `Chunker` (таймкоды, границы предложений), `PersonalityMapBuilder` с фейковым LLM-клиентом (`ai_client:` уже инжектируется) — секция `spoken_style`, обратная совместимость со старой картой, батчинг по размеру; `ContextBuilder` — выбор голоса по intent; `RagSearch` — метаданные и фильтры; `BuildTopicTreeJob` на фикстурных эмбеддингах; идемпотентность `ProcessRecordingJob`. LLM и эмбеддинги — всегда фейки.
- Выполнены обязательные меры из §5 с пометкой «Задача 2» (валидация LLM-очистки, дебаунс пересборки карты, кластеризация не в чистом Ruby, стабильность дерева тем).
- Приёмка: после подтверждения спикера в записи (Задача 1) чат отвечает на вопросы по содержанию видео со ссылкой «название, таймкод»; в карте появляется `spoken_style`, посты и речь не смешиваются в письменном режиме; страница «Темы» показывает дерево по нескольким записям; запрос «составь оглавление книги по всем выступлениям» возвращает оглавление из дерева с источниками; экспорт в Markdown работает; тесты/rubocop/brakeman зелёные.

**Вне объёма:** voiceprint и автосопоставление спикеров, правка расшифровки и границ реплик, генерация полного текста книги с версионированием, evals, подсчёт токенов тиктокеном (достаточно оценок по символам), собственные ASR-модели.
