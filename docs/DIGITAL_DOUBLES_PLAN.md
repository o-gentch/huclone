# Digital Doubles и общая библиотека — техплан

Статус: черновик на согласование. Код не написан.

## 1. Концепт

**Digital Double (DD)** — цифровая копия конкретного человека или роли: свой голос (карта личности), свои знания, свои инструкции, свои чаты и темы. У пользователя их может быть несколько: «я — автор канала про маркетинг», «я — автор канала про другое», «учитель английского».

**Библиотека** — все материалы пользователя (видео/аудио и тексты). Материал загружается и обрабатывается **один раз**, а затем подключается к любому числу DD.

```
Пользователь
├── Библиотека — видео и посты; расшифровка, спикеры, эмбеддинги считаются один раз
└── Digital Doubles
    ├── Подключённые материалы
    │     ├── видео: какие спикеры — этот человек (любые, в т.ч. выбранные у других DD; можно несколько; можно «никого»)
    │     └── пост: написан этим человеком или только знания
    ├── Карта личности (портрет) — только из речи/текстов этого человека
    ├── Инструкции — роль и поведение
    ├── Темы
    └── Чаты
```

Почему так:
- **Деньги.** Расшифровка оплачивается поминутно. Одно интервью, полезное двум DD, не загружается и не оплачивается дважды.
- **Изоляция.** DD ищет и учится только на своих материалах: маркетинг не смешивается с английским.
- **Разные люди в одной записи.** Интервью «я + преподаватель»: для моего DD берётся спикер A, для DD-учителя — спикер B.
- **Убрать ≠ удалить.** «Отключить от DD» не трогает материал; «удалить из библиотеки» — удаляет везде.

### Наименования (интерфейс пока на русском, локализация — отдельной задачей)

| Сущность | В интерфейсе | В коде |
|---|---|---|
| Цифровая копия | **Digital Double**, коротко **DD** (не склоняется: «Создать Digital Double», «DD «Мария»») | `Persona` (не переименовываем) |
| Все материалы | Библиотека | `Recording`, `Content` |
| Элемент библиотеки | Материал (видео / пост) | — |
| Карта личности | Портрет | `personality_map` |
| Связь DD ↔ материал | «Подключено к …» | `PersonaRecording`, `PersonaContent` |

Строки в новых и переписываемых экранах сразу выносим в `config/locales/ru.yml` через `t(...)` — чтобы английский потом был одним файлом.

## 2. Модель данных

### 2.1. Владение материалами переходит от персоны к пользователю

- `recordings.persona_id` → `recordings.user_id`. Уникальность дублей: `(user_id, source_checksum)` — повторная загрузка того же файла предлагает «уже в библиотеке — подключить к DD?».
- `contents.persona_id` → `contents.user_id`.
- `contents.speaker_id` (новое, для `kind: speech`) — чью речь содержит фрагмент.
- Статус записи заканчивается на расшифровке: `awaiting_speaker_confirmation` / `confirmed` заменяются на `transcribed` (дальше статус живёт у связи с DD).
- `speakers.is_persona` удаляется. `speakers.display_name` остаётся: имя спикера в записи общее («Ведущий», «Мария»).

### 2.2. Связи

**`persona_recordings`** — видео подключено к DD:

| Поле | Смысл |
|---|---|
| `persona_id`, `recording_id` | уникальная пара |
| `speaker_ids bigint[]` | кто из спикеров — этот человек; пусто = «его нет в записи» |
| `status` | `needs_speakers` → `ready` |

Ограничений между DD нет: один и тот же спикер может быть выбран у любого числа DD. Интерфейс лишь подсказывает «Спикер B выбран у DD «Учитель»».

**`persona_contents`** — какие фрагменты знаний доступны DD (материализованная выборка, по ней работают поиск, карта, темы):

| Поле | Смысл |
|---|---|
| `persona_id`, `content_id` | уникальная пара |
| `role` | `voice` — речь/текст этого человека (идёт в карту и в знания); `knowledge` — только в знания |
| `is_exemplar`, `included_in_map` | переезжают сюда из `contents`: эталоны и учёт в карте — свои у каждого DD |
| `persona_recording_id` | если строка появилась из подключённого видео (для каскадной синхронизации) |

Правила синхронизации:
- Подключили пост → строка `persona_contents` (`role: voice`, если отмечено «написано этим человеком», иначе `knowledge`).
- Выбрали спикеров у видео → строки для фрагментов этих спикеров (`role: voice`). Сменили выбор → лишние строки удаляются, новые добавляются.
- Отключили материал → строки удаляются, у DD чистятся `topic_chunks` этих фрагментов, ставятся пересборки карты и тем.

### 2.3. Обработка речи — лениво, по спикеру

Сейчас `Recordings::Ingest` строит фрагменты только для «персонального» спикера сразу после подтверждения. Новое правило:
- Расшифровка, спикеры и аудио — на уровне записи, один раз.
- Фрагменты речи (`TurnBuilder` → `SpeechCleaner` → `Content(kind: speech, speaker_id)` → эмбеддинги) строятся **для конкретного спикера при первом его выборе любым DD** и дальше переиспользуются.
- Повторный выбор того же спикера другим DD — бесплатно и мгновенно: только строки в `persona_contents`.

Открытый вопрос: включать ли в знания DD реплики **невыбранных** спикеров (вопросы ведущего, собеседник). Сейчас они попадают только как `context_text` к ответу. Предлагаю оставить так.

### 2.4. Кто что читает

| Компонент | Было | Станет |
|---|---|---|
| `Ai::RagSearch` | `contents.persona_id = ?` | `JOIN persona_contents WHERE persona_id = ?` (+ фильтр по `role` при необходимости) |
| `PersonalityMapBuilder`, `LinguisticsAnalyzer` | все `done`-материалы персоны | только `persona_contents.role = voice` |
| `ExemplarSelector` | `contents.is_exemplar` | `persona_contents.is_exemplar`, только посты с `role: voice`; плюс ручная отметка |
| `TopicTreeBuilder` | `contents.persona_id` | через `persona_contents` |
| `Quota` | через `recording.persona.user` | `recording.user` |
| `Imports::Telegram` | дубли по телу внутри персоны | дубли по `(user_id, channel, message_id)`; посты кладутся в библиотеку и подключаются к DD, если импорт начат со страницы DD |

## 3. Перенос текущих данных (одна миграция + задача)

1. `recordings.user_id = personas.user_id`, `contents.user_id = personas.user_id` (персоны без `user_id` — решить: удалить или привязать к единственному пользователю).
2. Для каждой записи: `persona_recordings(persona_id = старый persona_id, speaker_ids = [speaker с is_persona], status = ready | needs_speakers)`; статус записи `awaiting_speaker_confirmation`/`confirmed` → `transcribed`.
3. `contents(kind: speech).speaker_id` = «персональный» спикер их записи.
4. Для каждого content: `persona_contents(persona_id = старый persona_id, role = voice, is_exemplar, included_in_map)` — поведение сохраняется один в один.
5. Удалить `contents.persona_id`, `recordings.persona_id`, `contents.is_exemplar`, `contents.included_in_map`, `speakers.is_persona` — отдельной миграцией после проверки.

Карту личности и темы пересчитывать не нужно: состав материалов каждого DD не меняется.

## 4. Интерфейс

**Сайдбар**
- «Библиотека»
- Список DD (аватарка-буква, имя) + «＋ Новый Digital Double»
- Внутри выбранного DD: Материалы · Темы · Чаты · Настройки (инструкции, портрет)

**Библиотека** — один список видео и постов:
- поиск (название + текст; Postgres full-text), фильтры: тип, статус, источник (загрузка / Telegram-канал), «подключено к DD …» / «никуда не подключено»;
- группировка по источнику («Telegram · Канал X · 912 постов»);
- пагинация (50 на страницу);
- массовые действия: подключить к DD, удалить.

**Страница видео** (в библиотеке):
- плеер, расшифровка;
- блок «Подключено к»: для каждого DD — выбранные спикеры (чипы), «изменить», «отключить»; кнопка «Подключить к DD».

**Подключение видео к DD** — экран выбора спикеров (текущий, который нравится), но:
- вопрос «Кто из говорящих — {имя DD}?»;
- чекбоксы вместо радио (можно несколько) + «Этого человека нет в записи»;
- подсказка у спикера, если он выбран у других DD.

**DD → Материалы** — только подключённые; «Добавить из библиотеки» (поиск + мультивыбор) и «Загрузить» (загрузка идёт в библиотеку и сразу подключается к этому DD).

## 5. Этапы

1. **Модель и перенос данных** — `user_id` у материалов, `persona_recordings`, `persona_contents`, `contents.speaker_id`; RAG/карта/темы/квота читают через новые связи. Интерфейс почти без изменений. Критерий: тесты зелёные, чат и карта отвечают как раньше.
2. **Выбор спикеров у связи** — мультивыбор, ленивая обработка речи по спикеру, подсказки о других DD, смена выбора с синхронизацией.
3. **Библиотека** — общий список, поиск, фильтры, пагинация, группировка, массовые действия, подключение к DD, дубли по всей библиотеке.
4. **Несколько DD в интерфейсе** — сайдбар со списком DD, создание, настройки (инструкции, портрет), переименование в «Digital Double».
5. **Мелочи** — названия чатов по первому сообщению, удаление чатов, «Повторить» для упавших постов, ручные эталоны, дубли Telegram по `message_id`.

Позже: локализация (en), язык контента (язык расшифровки и ответов DD берётся из материалов/собеседника, а не из интерфейса).

## 6. Открытые вопросы

1. Название продукта: сейчас в интерфейсе «Аватар». Оставляем, или бренд тоже меняется (huclone / DD)?
2. Реплики невыбранных спикеров — только как контекст к ответу (предложение) или полноценные знания DD с пометкой «чья речь»?
3. Персоны без `user_id` (созданные до аккаунтов) — удалить или привязать?
